# xcrew-testbed

Xcode project fixtures in every form, generated by real tools.

One small app (a SwiftUI target and a unit-test target with a passing test, a seeded failure, a skip and an expected failure) is expressed as each form a project can take:

| Form | Made by |
|---|---|
| classic project with groups | XcodeGen, its spec removed |
| buildable folders | XcodeGen (`syncedFolder`), its spec removed |
| JSON `project.xcproj` | Xcode's `xcodeproj` tool (Xcode 27.2 and later) |
| XcodeGen | `project.yml` and the generated project |
| Tuist | manifests and the generated workspace |
| Tuist, not yet generated | manifests only |

Each form sits at the repository root of its fixture and again under `ios/`. `adversarial/` holds projects shaped to trip tools up, such as a source file named `Project.swift`. `modular/` holds apps split into modules across projects: `tuist-modules` is a Tuist workspace of three module projects in a chain, App on Feature on Core, each with its own test target. `captures/` holds what tools answered about a real run, committed so tests replay it: `repetitions` is a result bundle's test tree after five runs of three tests, one passing every run, one failing every run and one failing on every other run. `coverage` is what `xccov` answered about one test run with coverage on: whether the bundle has coverage, the files it holds, and one file's per-line counts, where the test runs one branch of `price(for:)` and not the other. `environment` is what MobileBuildMCP answered, through MCP, about builds that fail on the Mac rather than in the code, each with the build log it names: a corrupt module in Clang's module cache, a corrupt one among the SDK's precompiled modules, and an iPhone simulator name no simulator has. `snapshots` is three snapshot tests that fail, a square recorded red and rendered blue: swift-snapshot-testing under XCTest and under Swift Testing, and iOSSnapshotTestCase. It holds each failed test's attachments as `xcresulttool export attachments` gives them, from `xcodebuild test` and from MobileBuildMCP's `test_sim`. `uitests` is five XCTest UI tests under a test plan with two configurations, `Plan A` and `Plan B`: one taps a button that isn't there, one waits for a label the screen no longer shows, one fails an assertion after two taps that pass, one fails under `Plan B` only, and one passes. It holds each run's test tree, each failed test's activities and details, and its attachments, from `xcodebuild test` and from `test_sim`. Nothing nondeterministic runs outside the Mac that made it. `field/` is shaped like a large modular app seen in the field, with no identity: a Tuist workspace of four modules in layers (App on Feature on Data on Core), each importing and using the module below it, one scheme per module with coverage on in each, a UI-test target, `.xcode-version` pinned a major version behind the Xcode that generated it, and a CI workflow that selects Xcode from that file. Feature holds the scenarios' sources: an extension half tested, five probe tests (passing, failing, flaky every other run, skipped, expected to fail), a crash, and a line that compiles with a warning.

What the snapshot capture shows, with Xcode 27.2 and MobileBuildMCP 2.7.1:

- Both libraries attach the reference, the failing render and the difference as images, and xcresulttool marks none of them as associated with the failure (`isAssociatedWithFailure: false`). Only the issue's text is. So `export attachments --only-failures` leaves the images out.
- An image's suggested name is `<name>_<n>_<id>.png`: `reference`, `failure` and `difference` for swift-snapshot-testing, `Reference Image`, `Failed Image` and `Diffed Image` for iOSSnapshotTestCase. Under XCTest `<n>` counts 0, 1, 2 within one test; under Swift Testing each image is 0, in no set order.
- swift-snapshot-testing's XCTest images are exported without a file extension, though each is a PNG and its suggested name ends `.png`.

What the UI-test capture shows, with Xcode 27.2, iOS 27.2 (24B8117) and MobileBuildMCP 2.7.1, the test plan left at Xcode's defaults, on 2026-10-30:

- XCTest keeps a screen recording for each failed run of a test, one per configuration, and nothing for a passing run (`testPasses` has no attachments, and `testPlanA` has none under `Plan A`). It keeps no screenshot image at all. The recording starts with the test and stops at the failure: each lasts within 0.1 s of the time from its own `timestamp` to the failing activity's `startTime`. So its last frame is the screen at the failure.
- When a query fails (an element not found, a wait that ran out), XCTest adds the app's accessibility hierarchy twice, as text (`App UI hierarchy for <bundle id>`) and as an archived "UI Snapshot" (a binary property list), plus one "Debug description" of the query chain per attempt. An assertion on an element it found (`XCTAssertEqual` on a label) adds no hierarchy.
- The text hierarchy has one element per line, indented by depth: its type, its frame, and its `identifier` and `label` when set.
- In `get test-results activities`, the failing step is the one activity with `isAssociatedWithFailure: true`, and it holds the hierarchy attachments. In the export manifest, only a failed query's hierarchy is `isAssociatedWithFailure: true`. The recordings and the debug descriptions are `false`.
- Every attachment in the manifest names its `configurationName`, `deviceName` and `deviceId`, and each run in `activities` names its device and test-plan configuration. So a failure under one configuration only, `testPlanA` under `Plan B`, can be told apart without reading anything else.
- `test_sim` keeps the same kinds of attachment as `xcodebuild test`.
- The archived snapshots and synthesized events hold the device's id as text, so the capture numbers ids inside binary files too, and `leaks.sh` looks for them there.

The capture re-encodes the recordings at `avconvert`'s lowest preset to keep them small. They are real recordings, at a lower size.

`captures/field` holds what MobileBuildMCP's `test_sim` and `build_sim` answered about the field fixture's scenarios, with what `xcresulttool` and `xccov` answered about each run's bundle. The scenarios are:
- `probes`: the five probe tests, five times each, relaunched every time;
- `crash`: the crashing test, with its crash log;
- `coverage`: one test run with coverage on, and the half-tested file's line counts;
- `empty-filter`: a selection matching no test;
- `type-error`: a plain type error, with the pinned Xcode not the one building.

What the field captures show, with Xcode 27.2, iOS 27.2 (24B8117) and MobileBuildMCP 2.7.1, on 2026-10-30:

- On the repeated probes, MobileBuildMCP's text lists the flaky test once per failing run ("run 1 is odd", 3, 5) with no verdict, gives no skip reason, and doesn't count the expected failure. Its summary reads "2 tests failed, 1 passed, 1 skipped". The bundle's test list has each run.
- On the crash, the error text ("Index out of range") appears only among the errors. The failure line names the test with no file:line ("Crash: xctest at CrashTests.testOutOfRange()").
- A selection that matches no test reports "Test succeeded".
- A second build into the same DerivedData while another `xcodebuild` builds there succeeds, even with that `xcodebuild` stopped (SIGSTOP). The build runs in Xcode's build service, not in the `xcodebuild` process. So the field report's locked build database isn't reproduced here: it needs a stuck build service, which a capture must not cause, since Xcode itself shares it.

The crashing test crashes on purpose. Its capture step excuses exactly that one report, the test runner's with `testOutOfRange` in its crashing thread, for that step alone. Any other crash, before or after, stops the run as ever.

`leaks.sh` also fails on a temporary folder of this Mac (`/var/folders/…`, `/private/var/folders/…`, as written or JSON-escaped, in any file), which is what the captures' neutralisers rewrite. Adding it found one in `captures/environment/simulator-missing.log`, where `xcodebuild` had written an error result bundle into the Mac's own temporary folder. That file is fixed, and both neutralisers now map that folder too. It also fails on any user's home folder, not only this Mac's, and any Linux one, as xcrew's own privacy test checks every committed file: a crash log writes macOS's `USER` placeholder for one, which the field neutraliser now maps to `/testbed/user` like any other.

## Layout

```
base/               the app's sources and tests, shared by every fixture
forms/<fixture>/    one generated project per form and place
adversarial/<name>/ projects shaped to trip tools up
modular/<name>/     apps split into modules across projects
captures/<name>/     what tools answered about a real run, replayed by tests
scripts/generate.sh regenerates every fixture from base/
```

Each fixture has a `fixture.json`: its project definition, the generator and its version, where the project sits, and the Xcode that made it. A tool that uses the fixtures keeps its own expectations beside them, named for it: [xcrew](https://github.com/breferrari/xcrew), the first user, reads `expect.xcrew.json`.

## Regenerating

On a Mac with Xcode 27.2 or later, Node, and a released iOS runtime (not a beta):

```sh
brew install tuist xcodegen getsentry/xcodebuildmcp/mobilebuildmcp
scripts/generate.sh --build
```

`--build` also builds each form for testing, to prove it real. The captures run on a simulator of their own: an iPhone on the newest released iOS runtime, created for the run, booted once, and deleted at the end. A beta runtime's system apps can crash on boot, and nothing the captures do may crash anything on the Mac, so the run fails, naming them, when crash reports from that simulator appeared while it ran, except the known runtime crashes below, which it lists as ignored. Other reports that appear meanwhile, from the Mac's own apps, are listed without failing it. Regenerating keeps each fixture's expectations. It ends with `scripts/leaks.sh`, which fails when a fixture holds a path of the Mac that made it or the id of one of its devices or simulators; captures number those ids instead. The JSON forms' object IDs change on every run, because Xcode's tool picks them at random.

## Known runtime crashes

Crashes of Apple's runtime itself, which no capture causes. `generate.sh` lists them as "known Apple iOS 27.2 runtime crash, ignored" and goes on; `known_crash` holds them, and each entry goes once Apple's runtime no longer crashes.

**iOS 27.2 (24B8117) on macOS 27.2 (26B123), Xcode 27.2, 2026-10-30.** On a fresh iPhone 18 Pro Max simulator, launching any app crashes AppIntentsLiveEntityService and SettingsSearchReindexService about 30 seconds later. Nothing needs building: launching only Settings and Safari does it. Each crash is an `EXC_BREAKPOINT` whose crashing thread is in `XPCPeerRequirement.hasEntitlement` → `__XPC_API_MISUSE__`, under `XPCSystem.Session.handleReceivedRequest`; launchd restarts the service, and it crashes again. They show no crash dialog on the Mac. The probe that showed it:

| Time | Event |
|---|---|
| 15:15:58 | `simctl create`, then boot |
| 15:16:52 | booted and 30 s passed: no crash |
| 15:16:52 | `simctl launch com.apple.Preferences` |
| 15:16:53 | `simctl launch com.apple.mobilesafari` |
| 15:17:23 | SettingsSearchReindexService starts and crashes 0.2 s later |
| 15:17:26 | AppIntentsLiveEntityService starts and crashes 0.3 s later |
| 15:17:36 | AppIntentsLiveEntityService restarts and crashes again |

The same crashes came under macOS 27.0.1, and after `xcodebuild test` launched an app whether it was signed ad hoc or not signed at all.

**The same runtime, a fresh simulator, 2026-10-30.** During the snapshot capture's third test run (MobileBuildMCP's `test_sim`), assetsd, the Photos library service, started at 15:24:18 and aborted at 15:24:24 on an uncaught exception that PhotoLibraryServices threw in `PLLibraryServicesOperation` on the queue `PLLibraryServicesStateNode(…: prep-pre-migration)`: an `EXC_CRASH` with `SIGABRT`, about 3 seconds after the test run ended. Nothing the captures build uses Photos.

An entry joins `known_crash` only for an Apple system process, with only Apple frames in its crashing thread, and with evidence that no capture's code is involved. If yet another Apple process crashes, the list is the wrong tool: let the fresh simulator settle longer after boot instead.

## How xcrew uses it

xcrew's CI checks this repository out at a pinned commit and checks each fixture against `expect.xcrew.json`: what xcrew detects, what its setup writes, and what its doctor reports. Nothing is built in CI.
