# xcrew-testbed

Xcode project fixtures in every form, generated by real tools.

## The forms

One small app is expressed as each form a project can take. It has a SwiftUI target and a unit-test target with a passing test, a seeded failure, a skip and an expected failure.

| Form | Made by |
|---|---|
| classic project with groups | XcodeGen, its spec removed |
| buildable folders | XcodeGen (`syncedFolder`), its spec removed |
| JSON `project.xcproj` | Xcode's `xcodeproj` tool (Xcode 27.2 and later) |
| XcodeGen | `project.yml` and the generated project |
| Tuist | manifests and the generated workspace |
| Tuist, not yet generated | manifests only |

Each form sits at the repository root of its fixture and again under `ios/`.

## Layout

```
base/               the app's sources and tests, shared by every fixture
forms/<fixture>/    one generated project per form and place
adversarial/<name>/ projects shaped to trip tools up
modular/<name>/     apps split into modules across projects
field/              a large modular app's shape, with no identity
concurrency/        two frameworks and an app drawing Swift concurrency diagnostics
swift-testing/      a Swift Testing suite with each shape of result, and a Cancel scheme with a cancelled test
parallel/           an XCTest bundle its scheme runs in parallel
plans/              an XCTest bundle whose test plan has two configurations
captures/<name>/    what tools answered about a real run, replayed by tests
scripts/generate.sh regenerates every fixture from base/
```

- **`adversarial/`**: projects shaped to trip tools up, such as a source file named `Project.swift`.
- **`modular/tuist-modules`**: a Tuist workspace of three module projects in a chain, App on Feature on Core, each with its own test target.
- **`field/`**: shaped like a large modular app seen in the field, with no identity.
  - A Tuist workspace of four modules in layers: App on Feature on Data on Core, each importing and using the module below it.
  - One scheme per module, with coverage on in each, and a UI-test target.
  - `.xcode-version` pinned a major version behind the Xcode that generated it, and a CI workflow that selects Xcode from that file.
  - Feature holds the scenarios' sources: an extension half tested, five probe tests (passing, failing, flaky every other run, skipped, expected to fail), a crash, and a line that compiles with a warning.
- **`concurrency/`**: an XcodeGen project whose sources draw Swift concurrency diagnostics, each tagged with its compiler group.
  - Kit and Feature are frameworks in the Swift 5 language mode with complete concurrency checking. The `Warnings` scheme builds them: global mutable state, closures and values sent across isolation, one warning outside concurrency (`NoUsage`), and one with no group.
  - App is in the Swift 6 mode. Its global variable is an error, so the `App` scheme fails.
- **`captures/`**: what tools answered about a real run, committed so tests replay it. Nothing nondeterministic runs outside the Mac that made it. What each one holds and shows: [captures/README.md](captures/README.md).

Each fixture has a `fixture.json`: its project definition, the generator and its version, where the project sits, and the Xcode that made it.

## Regenerating

Needs a Mac with Xcode 27.2 or later, Node, and a released iOS runtime (not a beta).

```sh
brew install tuist xcodegen getsentry/xcodebuildmcp/mobilebuildmcp
scripts/generate.sh --build
```

- **`--build`** also builds each form for testing, to prove it real.
- **`scripts/generate.sh raw`** takes only the raw MobileBuildMCP test captures, on the capture simulator. **`RAW_CAPTURES`** names the ones to take again (`empty-filter`), keeping the folder's others. Unset, all of them are taken afresh.
- **`scripts/generate.sh multi-pass`** makes only `plans/` and takes the raw captures of runs that test a case more than once, and of a cancelled Swift Testing test, on one capture simulator.
- **`scripts/generate.sh neutral-paths`** rewrites every committed capture's `PATH` through `scripts/neutral-path.sh`, booting nothing; only `PATH` values change.
- **`scripts/generate.sh field-logs`** keeps the logs of committed field captures (`FIELD_CAPTURES` names which, `probes` unless named) from the MobileBuildMCP workspaces on this Mac, booting nothing. A log that's gone, or isn't a run of the test bed's `field/`, writes nothing.
- **`scripts/generate.sh raw-answers`** rereads the result bundles MobileBuildMCP kept for the committed raw captures and saves their answers, booting nothing. If any bundle is gone, or any answer fails, it writes nothing.
- **`scripts/generate.sh raw-session`** takes only the raw answers of MobileBuildMCP's session tools. Neither call persists, and the step stops if the project's config changes. Its simulator is created on a released runtime and never booted.
- **`scripts/generate.sh raw-build`** takes only the raw `build_sim` capture. It only builds: its simulator is created on a released runtime, never booted, and deleted at the end.
- **`scripts/generate.sh shapes`** makes only `swift-testing/` and its raw capture, on the capture simulator.
- **`scripts/generate.sh parallel`** makes only `parallel/` and its raw capture, on the capture simulator and at most two clones xcodebuild makes of it.
- **`scripts/generate.sh self-test`** checks the crash rules on made-up reports, and that a name other than a full run's boots nothing. It boots nothing itself.
- **A fixture's name** (`forms`, `adversarial`, `modular`, `field`, `swift-testing`, `plans`) makes only that fixture. `concurrency` and `parallel` are steps too, and take their captures. Any name that's no step's or fixture's stops with a usage line, having changed nothing. Only `scripts/generate.sh` or `--build` takes every capture but `multi-pass`'s, which has its own mode, and `xcode-mcp`'s, which needs Xcode open.
- **`scripts/generate.sh xcode-mcp`** takes the Xcode MCP's answers, and is never part of a full run. It needs the selected Xcode already open, by its own path, with `field/Field.xcworkspace` in it. Xcode then asks whether to let the caller in, which only the person at the Mac answers. It runs on this repository's fixture alone.
- **`scripts/generate.sh concurrency`** makes only `concurrency/` and its capture. That capture only builds: its simulator is created on a released runtime and never booted, and deleted at the end.
- **`FIELD_CAPTURES`** names the field scenarios to take again (`coverage type-error`), keeping the others' captures. Unset, all of them are taken afresh.
- **Expectations** survive: regenerating keeps each fixture's own.
- **Object IDs** in the JSON forms change on every run, because Xcode's tool picks them at random.

### The capture simulator

- **Its own.** An iPhone on the newest released iOS runtime, created for the run, booted once, and deleted at the end.
- **Crashes stop the run.** Nothing the captures do may crash anything on the Mac, and a beta runtime's system apps can crash on boot. So the run fails, naming them, when crash reports from that simulator appear while it runs.
  - The [known runtime crashes](captures/README.md#known-runtime-crashes) are the exception: the run lists them as ignored and goes on.
  - Reports from the Mac's own apps that appear meanwhile are listed without failing it.
  - The field capture's crashing test crashes on purpose. Its step excuses exactly that one report, for that step alone.
- **Cleanup on stop.** A run stopped any way (HUP, INT, TERM, or a job-control stop) still deletes its simulator. No step reads a terminal.

### Leaks

The run ends with `scripts/leaks.sh`. It fails when a committed file holds:

- a path of the Mac that made it: its home folder or this checkout;
- the id of one of its devices or simulators, binary files included, since an archived attachment can hold one as text. Captures number ids instead, from `00000000-0000-0000-0000-000000000001`;
- a temporary folder of the Mac (`$TMPDIR`, with or without its `/private` prefix), as written or JSON-escaped, in any file;
- any user's home folder, not only this Mac's, macOS's `USER` placeholder included, and any Linux one;
- a `PATH` with an entry other than an Xcode app's own and macOS's defaults, which would name the Mac's own tools. `scripts/neutral-path.sh` holds the rule, which every step writes through and `scripts/generate.sh neutral-paths` applies to committed files in place. Other variables whose names end in PATH (`MANPATH`, `INFOPATH`, `DYLD_LIBRARY_PATH`) are left alone on purpose: they name the system's and Homebrew's usual folders, not the Mac's own tools.

Paths count as written or with JSON's escaped slashes (`\/`).

## How xcrew uses it

- A tool that uses the fixtures keeps its own expectations beside them, named for it. [xcrew](https://github.com/breferrari/xcrew), the first user, reads `expect.xcrew.json`.
- xcrew's CI checks this repository out at a pinned commit, with its tag beside it.
- It checks each fixture against `expect.xcrew.json`: what xcrew detects, what its setup writes, and what its doctor reports. Nothing is built in CI.
